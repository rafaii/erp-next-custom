# ADR-0010: PDC Schedule Generation & Bank Reconciliation

- **Status**: accepted
- **Date**: 2026-08-24
- **Deciders**: Imran
- **Supersedes**: -
- **Superseded by**: -

## Context

ADR-0005 designed a PDC-driven payment schedule: `build_payment_schedule` reads
existing `PDC Entry` records for a lease and uses their `check_date`s as the
`Rent Schedule` due dates, falling back to a plain monthly cadence when no
PDCs exist. In practice **nothing in the app ever creates a `PDC Entry`** —
there is no UI for it anywhere (checked: absent from the New Lease dialog,
absent from the Contract detail page, only ever read in aggregate on the
Accounts KPI page). Every lease today silently falls back to the monthly
cadence, and the PDC path is dead code.

Separately, once a `Sales Invoice` is generated by the daily scheduler
(ADR-0004), nothing ever marks it paid — no `Payment Entry` is created
anywhere in the codebase. Rent collection today is entirely invoice-only;
tracking whether the physical cheque backing that invoice actually cleared
the bank doesn't exist.

The business process this needs to model: a tenant hands over N post-dated
cheques at signing (one per rent period, consecutively numbered, drawn on a
Qatari bank). On each cheque's date, the company deposits it; when the bank
confirms clearance, the corresponding invoice should show as paid. The
security deposit is collected separately (cash or a single cheque) and is
not part of the recurring rent cadence.

## Decision

1. **`Security Deposit` — new standalone DocType, separate from `PDC Entry`.**
   Fields: `lease` (Link, reqd — traces every deposit back to its contract
   and, through the lease, its tenant), `customer` (fetched), `amount`,
   `deposit_type` (Cash / Cheque), `check_number` + `tenant_bank` (reqd only
   when Cheque), `status` (Held / Refunded / Forfeited), `held_date`,
   `refunded_date`. One row per lease, created alongside the lease (not by
   the schedule generator). No GL/liability posting in this slice —
   record-keeping and portal visibility only; formal escrow accounting is a
   future slice. Surfaced as a linked-record panel on **both** the Lease
   Agreement (Contract) page and the Customer (Tenant) page — the latter via
   a small method-based lookup (same pattern as `get_building_leases`),
   since Customer has no direct link field to it.

2. **`PDC Entry` gains `tenant_bank`** (Link → the new `Cheque Bank`, see
   below — distinct from the existing `bank_account`, which is the
   *company's* deposit account) **and `sales_invoice`** (Link → `Sales
   Invoice`, set once that PDC's schedule row is invoiced — lets
   reconciliation find the invoice directly instead of matching by date).

3. **New `Cheque Bank` DocType — a simple, tenant-managed lookup list, not
   ERPNext's core `Bank`.** Just `bank_name` (Data, unique). Deliberately
   separate from `Bank`/`Bank Account` (which back GL reconciliation, Plaid,
   etc.) — this is purely "which bank issued this cheque," shared across all
   of a company's customers and PDCs. No seeding/fixture data: each tenant
   site starts empty and builds its own list. Managed two ways: (a) a
   "Manage Banks" list reachable from the Settings page, reusing the
   existing generic doctype list/detail views (ADR-0006) — no bespoke CRUD
   UI; (b) inline from the PDC / Security Deposit bank field itself — an
   "+ Add bank" affordance that quick-creates a `Cheque Bank` row and
   selects it immediately, for the common case of a bank not yet on file.

4. **Schedule generation becomes an explicit, user-controlled action** —
   `generate_pdc_schedule(lease, count=12, start_check_number, payment_day,
   tenant_bank)` — not an implicit read of pre-existing records. It:
   - Creates `count` `PDC Entry` rows, one per `payment_frequency` period
     from `start_date`, dated on `payment_day` of each period, numbered
     sequentially from `start_check_number` (zero-padded).
   - Rebuilds `Rent Schedule` from those rows (reuses the existing
     `_pdc_schedule_rows` path in `build_payment_schedule`), pairing each
     schedule row to its originating PDC via a new `pdc_entry` link field on
     `Rent Schedule`.
   - Is re-generatable only while **every** PDC for the lease is still
     `Pending` (delete + recreate); once any row has left `Pending`
     (Deposited/Cleared/Bounced), regeneration is blocked — a partial-period
     remainder or a correction is instead added/edited as an individual `PDC
     Entry` row, same as any other record.
   - `count` defaults to what the lease's date range implies but is always
     editable — nothing generates without this call.

5. **Two-stage processing, split by what the system can actually know:**
   - **Deposit (automatic).** Extend the existing daily scheduler
     (`generate_due_invoices`'s job) to flip `Pending` → `Deposited` for any
     PDC whose `check_date` has arrived — "sent to the bank" is a fact the
     system owns, not an external one.
   - **Clearance (manual, staff-confirmed).** Whether a cheque actually
     cleared is bank-side truth we don't have a feed for. Staff mark a
     `Deposited` PDC `Cleared` or `Bounced` (single or bulk action on the
     Accounts page) once the bank statement confirms it. Marking `Cleared`
     auto-creates and submits a `Payment Entry` against the PDC's linked
     `sales_invoice`, reconciling it to Paid. Marking `Bounced` leaves the
     invoice outstanding and flags it via `add_activity`; no automatic
     replacement PDC is created — that's a manual correction, same as any
     other bounced-cheque handling today.

## Alternatives Considered

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| Security deposit as a field on `PDC Entry` (a `type` flag) | One less DocType | Mixes a one-off refundable deposit with a recurring rent-cheque ledger; conflates two different lifecycles (Held/Refunded vs Pending/Deposited/Cleared) | rejected — explicit user requirement to keep separate |
| Auto-clear PDCs on `check_date` (no manual confirmation step) | Fully automated, invoices "pay themselves" | Would mark rent as collected before the bank has actually confirmed it — an accounting integrity risk with no bank feed to back it | rejected |
| Add `country` field to core `Bank` doctype, filter by company country | More "correct" schema | Modifies an ERPNext core doctype for a single-tenant-per-site concern already solved by ADR-0003; also conflates GL bank accounts with tenant-cheque banks, which the user explicitly wants kept separate | rejected |
| Fixture-seed a fixed bank list (original draft) | Zero data entry | Not user-editable per tenant; wrong model — banks should be built up by each company as needed, not preloaded | rejected — superseded by user feedback |
| Keep schedule generation implicit (as today) | No new whitelisted method | Already proven dead — nothing creates the PDCs it depends on | rejected |

## Consequences

### Positive

- Completes the PDC path ADR-0005 designed but never got a UI for.
- Rent collection state (Pending → Deposited → Cleared/Bounced) becomes
  visible and drives real invoice reconciliation via `Payment Entry`.
- Security deposit lifecycle (Held/Refunded/Forfeited) tracked distinctly
  from recurring rent cheques, as required.
- Regeneration guard prevents silently discarding cheques already in flight.

### Negative

- Two new DocTypes (`Security Deposit`, `Cheque Bank`) and two new fields on
  `PDC Entry` / `Rent Schedule` to migrate.
- Clearance remains a manual staff step (by design) — no bank feed
  integration in this slice.
- Each tenant site starts with an empty bank list and builds it up as
  cheques come in — acceptable since the inline "+ Add bank" affordance
  makes this a zero-friction, one-time cost per bank rather than a setup
  step.
